# Localisation

MKLight's apps show English and Simplified Chinese (`zh-Hans`). The engine
stays English and its API does not change: each app translates its own UI
from its own catalog, and the text the engine hands it through one shared
catalog. Terms come from one glossary, so the three apps and the engine text
say the same thing.

| What | Where | Format |
|---|---|---|
| Glossary | `locales/zh-Hans/GLOSSARY.md` | English term → 简体中文, style rules |
| Engine text | `locales/zh-Hans/engine.json` | JSON, below |
| macOS UI | `apps/macos`, `Localizable.xcstrings` per target | String Catalog |
| Web UI | `apps/web/src`, typed catalogs (one TypeScript module per locale) | `en` is the source; the others must have every key |
| Windows UI | `apps/windows/src`, `Strings/<locale>/Resources.resw` | `.resw`, `x:Uid` in XAML |

## Locale selection

The apps follow the system language (the browser's on the web). The first
preferred language that MKLight has decides:

* `zh`, `zh-CN`, `zh-SG` and any `zh-Hans*` → `zh-Hans`;
* `zh-TW`, `zh-HK`, `zh-MO` and any `zh-Hant*` → English for now (no
  Traditional Chinese yet);
* anything else → English.

The web app also has a language picker; its choice is kept per browser and
wins over the browser language. The macOS and Windows apps use the per-app
language of the system settings.

## Engine text

The engine catalog is one JSON object per language:

```json
{
  "locale": "zh-Hans",
  "strings":     { "<exact English text>": "<中文>" },
  "enums":       { "<enum value>": "<中文 label>" },
  "diagnostics": { "<diagnostic code>": "<中文 template>" }
}
```

An app loads it once at start (bundled as a resource; on the web as a
JSON module of the locale's chunk) and looks text up only where it displays
it. Anything the app parses, matches or sends back stays the engine's
English or identifier: the regular expressions on setting descriptions, the
remedy and scope matching of run warnings, surface numbers in messages,
enum values in settings.

### `strings`

Exact match on the whole English string as the engine emits it: same case,
same punctuation, no trimming. A miss shows the English. Look up:

* analysis descriptors: `title`, `description`, `unavailable_reason`;
* settings schemas, at every depth: `title` (also of `oneOf`/`anyOf`
  variants) and `description`. Not `unit`, keys, defaults or `enum`;
* `first_order` results: `entries[].label`;
* field map results (`pupil_aberration`, `relative_illumination_map`,
  `chief_ray_angle`): `columns[].definition`.

An app that shows an engine string with its own changes (first letter
capitalised, a prefix) looks up the engine's string first and applies its
change to the English only.

### `enums`

Keyed by the raw value of a settings `enum` (`hexapolar`, `monte_carlo`). A
hit is the label to show; a miss falls back to the app's own formatting of
the value (`siemens star`, `Monte Carlo`). The value written to settings is
always the raw one. Axes and planes (`x`, `y`, `xz`, `yz`) have no entry and
show as they are. One value has one label in every setting, so a label must
fit each setting listed for it in `target/i18n/engine-en.json`.

### `diagnostics`

Keyed by the diagnostic code. Two kinds of issue carry one:

* `validate` issues (`issues[]` of the result, `mk_session_validate_json`):
  `{severity, code, surface, message}`, codes in RESULTS §6;
* structural issues (CONVENTIONS §13): the error of an invalid model,
  `invalid model: [code] path: message`. Read `code` and `path` with
  `\[([a-z_]+)\] ([^:]+): (.*)`.

The template is a complete sentence that replaces the issue's text. It may
use `{surface}` (the issue's `surface`, shown as the app shows surface
numbers elsewhere) and `{path}` (the structural issue's JSON path, shown in
monospace), and no other placeholder. Show the English `message` with it, as
detail (a tooltip or a second line): it holds the values a template leaves
out (the material name, the number that is out of range). Fall back to the
English message when the code has no template or a placeholder's field is
null.

### Text that stays English

These reach the user in English in every language, because the engine builds
them with values inside and gives no code or fields to rebuild them from:

* run warnings (`run_info.warnings`), `backend.fallback_reason`, failed
  attempt reasons, GPU preparation messages;
* error messages (`EngineError`, `MkError`) other than the structural
  issues above, and job failure reasons;
* import warnings (`message`; the `kind` is the app's to name), glass
  catalogue warnings, `open_warnings`, solve report warnings, per-operand
  `error`;
* compute backend titles and reasons.

An app wraps them in its own translated context ("运行警告：", "导入时"),
not in a translation of its own.

### Checking and filling the catalog

`crates/mklight-engine/tests/i18n.rs` collects the engine text from the live
engine (the analysis registry, a `first_order` run and the field map runs)
and the diagnostic codes from the code that emits them. It fails when a
catalog misses an entry, keeps one the engine no longer emits, has an empty
translation, or uses another placeholder. `scripts/i18n-check.sh` runs it:
the failure lists the missing entries as JSON to paste in, each with where
it comes from (`spot_diagram.settings.rays.description`), and the script
writes the whole English list with sources to `target/i18n/engine-en.json`.

## Shared UI text

`locales/<id>/ui.json` translates once the UI text two or more apps share,
so the apps cannot drift apart. The apps keep their native catalogs and
nothing changes at run time; a script copies the shared translations in.

```json
{
  "locale": "zh-Hans",
  "strings": { "<English, placeholders as {0}, {1}…>": "<中文>" },
  "context": { "<English>": "<why it is translated per app>" }
}
```

* **Shared:** an English string, after placeholder normalisation, that is
  in two or more apps. Exact match, case-sensitive. Placeholders become
  `{0}`, `{1}`… in order of first appearance in the English: macOS `%@`,
  `%lld`, `%1$@` (and `%%` as `%`), web `{name}`, Windows `{0}`, `{1:0.0}`.
  Each app gets its own placeholders back.
* **Left out:** web plurals (`{one, other}`), strings with no letter
  outside placeholders, macOS strings marked not to translate. Strings only
  one app has stay in its catalog.
* **`context`:** the same English with different meanings (`Stop`: 停止 or
  光阑; `Radius`, `Source`, `Conic`) or a platform convention (`Copy`,
  `OK`). Each app translates these itself.

`node scripts/i18n-ui.mjs`, no dependencies:

* `extract`: reads the three catalogs, adds the shared strings all apps
  already agree on to `ui.json`, and lists the conflicts (same English,
  different translations, with each app's text and key) and what it
  skipped. Resolve a conflict in `strings`, or list it in `context` with a
  reason.
* `apply`: writes `ui.json` into every app catalog that differs. It edits
  only the translated text, in place: the String Catalog keeps Xcode's JSON
  layout, the `.resw` its XML (only `<value>` text), the web modules their
  literals. Running it twice changes nothing.
* `check`: what the test checks.

`apps/web/src/i18n/shared-ui.test.ts` (part of `pnpm exec vitest run`, so it
runs on the Mac and the Windows machine) fails when an app's translation of
a shared string differs from `ui.json`, a shared string is missing from it,
an entry is no longer shared, or the Windows `.resw` is not well-formed or
lost an en-US key or placeholder.

## Adding a string

* **Engine:** write the English in the engine as usual, run
  `scripts/i18n-check.sh` and add what it lists to every catalog. A changed
  English string is a new key: translate it again and drop the old one.
  Text that should be translatable but is formatted with values belongs in
  a field or a code with a template, not in a sentence.
* **App UI:** add the string to the app's own catalog in English and every
  other language, with the glossary's terms. Do not put engine text into an
  app catalog. If another app has the same English, the test asks for it in
  `ui.json`: run `extract`, resolve, then `apply`.
* **Term:** add it to the glossary first, then use it.

## Adding a language

1. Pick the locale id the platforms share (BCP 47, script subtag where it
   matters: `zh-Hant`, `ja`, `de`) and add it to each app's locale
   selection.
2. Copy `locales/zh-Hans/GLOSSARY.md` to `locales/<id>/` and translate the
   right-hand column; keep the style section's intent.
3. Create `locales/<id>/engine.json` from `target/i18n/engine-en.json`
   (keys only) and translate it; `scripts/i18n-check.sh` checks every
   locale it finds.
4. Translate the shared UI text: copy `locales/zh-Hans/ui.json` to
   `locales/<id>/ui.json`, translate `strings` (keep `context`'s keys), and
   once step 5 has created the catalogs, run
   `node scripts/i18n-ui.mjs apply <id>`.
5. Add the language to the macOS String Catalogs, a web catalog module and a
   Windows `Strings/<id>/Resources.resw`; translate what `apply` left: each
   app's own strings and its `context` entries.
